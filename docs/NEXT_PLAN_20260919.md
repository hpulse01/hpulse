### 1.2 任务明细

#### T1 · 恢复 GitHub Actions 并取得首条 CI 绿灯（P0）
- **目标**：结束「零 job startup_failure」状态，让 `ci.yml` 的 rust → web → android/ios 四个 job 至少在 `main` 上完整跑通一次。
- **依赖**：仓库 Owner 检查 Actions 开关、私有仓库计费/分钟额度、组织策略（`Settings → Actions → General`）；必要时先用 `workflow_dispatch` 触发。
- **AC**：
  1. `gh run list` 出现 `success` 的 `H-Pulse CI` 运行，四个 job 全绿；
  2. `hpulse-input-wasm` 与 `hpulse-android-debug` artifact 可下载，`verify:runtime-assets` 通过；
  3. `docs/COMMERCIAL_RELEASE_GATES.md` 与 `COMMERCIAL_BETA_READINESS.md` 删除「Actions startup_failure」阻断项并记录首次绿灯 run URL。
- **备注**：若 Owner 无法在 W1 恢复，备选是自托管 runner 或临时迁移到其它 CI；但 CI 证据仍是 TestFlight/Play 内测前置门禁，不能跳过。

#### T2 · 凭据轮换 + 合并 PR #20（P0）
- **目标**：消除 PR #20 描述中的两类风险：历史 `SECURITY DEFINER` 函数信任调用方传入的 `p_admin_id/p_user_id`；Git 历史中存在已暴露凭据。
- **依赖**：T8 的 staging 项目（可先用临时 Supabase 项目）；Supabase 管理员权限。
- **AC**：
  1. 已暴露凭据轮换完成，相关会话已吊销，操作记录在 `docs/SECURITY_LOG.md`（新建，不含任何密钥值）；
  2. PR #20 迁移链在 staging 从零应用成功；anon / authenticated / admin / super_admin / service_role 五类调用用例各有一条通过记录；
  3. `npm run security:static` 在 main 上通过；PR #20 由 draft 转为 ready 并合并；
  4. 明确记录「Git 历史清理（history rewrite）」是否执行；若不执行，以凭据失效为补偿控制。

#### T3 · 简报/仓库对齐（P0）
- **目标**：让 GitHub `main` 成为唯一事实源；把简报提到但仓库缺失的资产找回或明确其状态。
- **依赖**：访问本机 `/workspace/repos/hpulse` 工作区与 Lovable 项目；用户/幕僚长确认。
- **AC**：
  1. `AGENT_MISSION.md` 入库（若本机存在则原样提交；若不存在则以本文档第 0.2 节假设 A1 为据新写，并标注「重建稿」）；
  2. 确认 P6.1 LifeTimeline 代码是否存在于任何未推送分支或 Lovable 变更；有则推送为独立 PR，无则在 `ROADMAP.md` 把 P6.1 改回「计划中」；
  3. `docs/hpulse/03-dynamic-weights.md`、`04-engine-runners.md` 引擎数由 10 更正为 13，并与 `ALL_ENGINES` 对齐；
  4. README 增加一行「命名对照：H-Pulse（产品）/ hpulse-mobile（包）/ Iron Plate Oracle（Lovable 旧显示名，待改）」。

#### T4 · LifeTimeline 数据契约 + 纯函数派生器（P1）
- **目标**：把「按时间展开的生命轨迹」从 UI 组件变成可测试、可审计的数据层，节点可回溯到引擎与规则。**只做 schema 与派生函数 + 测试；UI 复用现有 `EventTimelinePanel` / `YearByYearPanel`，不新增视觉工程。**
- **依赖**：T3 结论（若 P6.1 代码存在则以其为基础重构而非重写）；`TimeWindow`、`eventCandidates`、HPU-5 `WorldTree.stages` 现有输出。
- **建议契约**（放在 `src/types/lifeTimeline.ts`，同时写入 `docs/LIFE_TIMELINE.md`）：

```ts
interface LifeTimelineNode {
  id: string;                     // 由 seedMaterial + age + dimension 确定性派生，非随机
  age: number; year: number;      // year = birthYear + age，不读系统时钟
  dimension: FateDimension;       // 10 维之一
  eventClass: 'career' | 'wealth' | 'love' | 'health' | 'family' | 'study' | 'migration' | 'turning_point' | 'general';
  trend: 'rising' | 'stable' | 'declining';
  confidence: number;             // 0..1，已按 status/grade 封顶后的值
  supports: Array<{ engine: EngineName; ruleId?: string; implementationStatus: string; sourceGrade: string; traceRef: number }>;
  boundaryNote?: string;          // 例如「分析边界，不是寿命估计」
}
interface LifeTimeline { schemaVersion: 'lt-1.0.0'; algorithmVersion: string; nodes: LifeTimelineNode[]; horizonAge: number; disclaimers: string[] }
```

- **AC**：
  1. `buildLifeTimeline(unifiedResult | PipelineReport): LifeTimeline` 为纯函数，同输入字节级相同输出（新增 determinism 测试）；
  2. 每个节点 `supports` 非空，且 `confidence ≤ min(引擎 cappedConfidence)`；
  3. 不产生任何触发 `UNSAFE_MORTALITY_PATTERNS` 的文本（复用 `commercialReadiness` 的扫描器写测试）；
  4. 「学业 / 迁移 / 家庭」三类简报要求的领域在 `eventClass` 中有显式映射，映射表写入 `docs/LIFE_TIMELINE.md`；
  5. 结果页在非超管视图下可见轨迹，但每个节点显示 `implementationStatus` 徽章与置信度；命运树/唯一路径继续限超管。

#### T5 · P7 启动：规则 ID 化 + 首批黄金用例（P1）
- **目标**：让 `ALGORITHM_VERIFICATION_MATRIX.md` 的「晋级 complete 六条件」有可执行载体，选 **缺口最小** 的引擎先跑通全流程，而不是全面铺开。
- **候选顺序与理由**：
  1. **Numerology**（PR #21 合并后仅剩「非 A–Z 转写口径」+ 独立 corpus）→ 最可能成为首个 `complete` 候选；
  2. **Mayan**（缺 819 日周期与金星周期；GMT 584283 相关系已固定）；
  3. **Western 天文层**（行星黄经对 JPL Horizons 固定 corpus 做数值比对，验证的是 `astronomy-engine` 集成而非占星解释）。
- **依赖**：T6；来源文献可引用（URL/ISBN/DOI）；`scripts/` 下新增 corpus 生成/校验脚本时不得依赖本机绝对路径（现有 `build-ziwei-corpus.ts` 写到 `/mnt/documents`，应参数化）。
- **AC**：
  1. `algorithmSourceRegistry.ts` 每条 `implementedRules` 具备 `ruleId`（形如 `numerology.lifepath.v1`）与 `reference`（稳定引用），Schema 变更有 Zod/TS 类型与测试；
  2. `fixtures/golden/<engine>/` 目录建立，Numerology ≥ 30 例、Mayan ≥ 30 例（含边界与非法输入），Western 行星黄经 ≥ 20 个时刻 × 10 行星与 Horizons 差值 ≤ 0.01°（阈值写入文档）；
  3. `explanationTrace` 至少在这三个引擎中每步携带 `ruleId`（结构化 trace 见第 2.1 节）；
  4. **本阶段不把任何引擎标为 `complete`**；每个引擎新增一份 `docs/verification/<engine>.md` 记录距离 complete 的剩余条件。

四周结束时 **仍然预期 `complete = 0`、门禁仍 Blocked**——这是诚实的结果。本计划的产出是「证据链可运转 + 轨迹有数据契约 + 首个引擎距离 complete 的剩余条件可数」。

## 2. 系统设计完善建议

### 2.1 架构

1. **双核收敛路线要写成 ADR，而不是任其并存。** `src/core/`（P4）与 `src/hpulse/`（HPU）目前都能产出 `EngineOutput`；`quantumPredictionEngine.ts`（1446 行）与 `src/hpulse/orchestrator/pipeline.ts` 是两条融合路径。建议：HPU 管线成为唯一正式路径，`quantumPredictionEngine` 降为兼容适配器；每个引擎切换时用「同输入双跑、输出 diff 为零」作为切换验收。
2. **结构化 `explanationTrace`。** 现契约为 `string[]`。建议在不破坏旧 UI 的前提下新增 `explanationSteps: Array<{ ruleId, inputs, output, reference }>`，`explanationTrace` 由它渲染生成。这是 T4「节点回溯到规则」和 T5「规则 ID 化」的共同基础。
3. **`algorithm_version` 组合化。** 目前 `wmat-1.1.0`、`wtree-1.0.0`、`projection-1.0.0` 等分散；建议在 `PipelineReport` 顶层放一个 `algorithmVersion` 复合对象（各引擎版本 + 矩阵版本 + 树版本 + 输入 schema 版本），并写入 `prediction_runs.algorithm_version`，保证账本回放时可精确定位。
4. **黄金用例目录制度化。** 建立 `fixtures/golden/<engine>/{normal,boundary,invalid,ambiguous}.json`，配 `scripts/verify-golden.mjs`，纳入 `npm run check`。任何引擎 PR 若改变 golden 输出必须显式更新 fixture 并在 PR 说明原因。
5. **脚本可移植性。** `scripts/build-ziwei-corpus.ts` 依赖 `/mnt/documents` 绝对路径与 `bun`；统一改为参数化输出目录并用 Node 运行，纳入 CI。
6. **WASM 路径的双轨维护成本。** Rust `hpulse-input` 只覆盖输入归一化，其它逻辑全在 TS。建议 ADR 明确：短期内 Rust 只做输入契约，不扩展到引擎，避免两语言维护 13 套规则。

### 2.2 产品

1. **轨迹优先，报告其次。** 首屏应为 LifeTimeline（阶段 → 节点 → 支撑引擎），静态分区报告收进二级 Tab。每个节点必须同时显示：置信度、`implementationStatus` 徽章、支持引擎数、以及点击展开的规则引用。
2. **领域覆盖显式映射。** 简报要求覆盖事业/财富/情感/健康/家庭/学业/迁移/重大转折；`FateVector` 10 维中没有「学业」「迁移」，HPU-3 的事件轴有 `migration` 但无 `study`。建议在 T4 的 `eventClass` 中补齐并写映射表，而不是新增 FateVector 维度（避免破坏 0..100 十维契约与账本兼容）。
3. **诚实分层的文案系统。** 文案按引擎状态自动切换措辞：`partial` 用「依据 X 规则显示倾向」，`needs_source_validation` 用「研究模式，未经底本校验」；禁止出现「必然」「注定」。文案模板与 `implementationStatus` 绑定并有快照测试。
4. **反馈入口就地化。** 在轨迹节点上直接「标记已发生 / 未发生」写入 `prediction_actuals`，比独立账本页更能积累 P8 样本；同时提示用户反馈不会改变已生成结果（确定性）。
5. **中英一致与命名统一。** 统一产品名为 H-Pulse；Lovable 显示名、`index.html` title、商店名称一致；「铁板神数」只作为引擎名出现。
6. **超管审计视图与用户视图分离维护。** 命运树/唯一路径继续超管专属，直到 T7 决策与 T5 首个 complete 引擎出现；用户视图只消费 `LifeTimeline`。

### 2.3 审计

1. **把「晋级 complete 六条件」做成可执行检查。** 新增 `src/core/shared/promotionGate.ts`：读取注册表 + golden 覆盖率 + 校准样本量，输出每引擎「距离 complete 的剩余条件列表」，并在超管审计页展示。人工不得绕过。
2. **账本反作弊与最小样本量。** `ledgerScoring.ts` 目前任何一条 actual 都计入；应加去重、同一 run 同领域同年只计一次、以及 §T10 的样本门槛，防止少量自报导致 `hitRate` 虚高。
3. **敏感内容扫描扩展到轨迹层。** `UNSAFE_MORTALITY_PATTERNS` 现在扫 `EngineOutput`；`LifeTimeline` 和任何 AI 解读输出也必须过同一扫描器，并保留回归测试。
4. **审计报告版本化归档。** 每次 `main` 合并生成 `implementationAudit` 快照（JSON）存入 `docs/audit-snapshots/YYYYMMDD.json`，让「引擎状态随时间的变化」可追溯。
5. **AI 解读的边界审计。** `ziwei-rag-explain` 等 Edge Function 属「解释层」，应在响应中携带 `deterministicInputsHash`，并在 UI 标注「AI 解读为非确定性辅助文本，不进入轨迹与账本」。

### 2.4 发布

1. **四通道门禁分层**（详见 T9）：Lovable preview（无门禁，仅设计验证）→ Lovable published（CI 绿 + 安全 PR 合并 + 文案一致）→ Supabase staging（迁移可重放 + 删户 e2e）→ 商店内测（`COMMERCIAL_BETA_READINESS.md` 全部「内测前」项）→ 公开商业发布（`COMMERCIAL_RELEASE_GATES.md` 十条全过、`ready === true`）。
2. **Lovable unpublished changes 的建议时机**：不早于 T1 + T2 + T3 完成；且只有当 diff 审查确认不含算法/Supabase 变更、或已回流合并后，才发布。若 diff 中含 P6.1 LifeTimeline 代码，应先回流 GitHub 走 PR，而不是在 Lovable 直接发布。
3. **版本号与变更日志。** `0.1.0-beta.1` 之后每次可交付构建递增 `beta.N`，`CHANGELOG.md` 按「算法 / 审计 / UI / 安全 / 文档」分类，算法条目必须引用 ruleId 或 fixture。
4. **免费 beta 期间禁止任何支付代码**（ROADMAP 已明示），门禁脚本可加静态扫描规则拒绝引入 IAP/支付 SDK。

## 3. 风险与依赖

### 3.1 技术风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| GitHub Actions 持续不可用 | 所有「CI 证据」门禁无法满足；原生构建无产物 | T1 优先；备选自托管 runner；在门禁文档保留阻断项直到恢复 |
| 双核并存导致融合口径分叉 | 同输入两条路径给出不同结果，削弱「确定性」叙事 | 2.1-1 ADR + 双跑 diff 测试 |
| `quantumPredictionEngine.ts` 体量过大 | 修改风险高、审计困难 | 只做适配器化拆分，不重写算法 |
| 黄金用例来源不足或不可引用 | 引擎无法离开 `partial` | T5 先挑缺口最小引擎；引用必须为 URL/ISBN/DOI |
| WASM 构建依赖 `wasm-pack 0.13.1` 与 Rust stable 漂移 | CI 偶发失败 | 锁定 toolchain 文件；产物校验已存在 |

### 3.2 合规风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| Git 历史中已暴露凭据 | 账户/数据被未授权访问 | T2 立即轮换并吊销会话；决定是否重写历史 |
| 特权 RPC 信任调用方 ID | 越权提权、配额绕过 | 合并 PR #20 |
| 铁板条文库版权/授权不明 | 公开发布法律风险 | T7 ADR；公开路径继续脱敏 |
| 占卜类应用在部分地区/商店的审核政策 | 上架受限 | 法务审查纳入公开发布门禁；文案坚持「文化研究/娱乐/自省」定位 |
| 未成年人与敏感领域（健康）内容 | 消费者保护风险 | 年龄限制、健康维度措辞限定为「倾向」，禁止医疗建议 |

### 3.3 数据风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 出生时间/地点属敏感个人数据 | 泄露后果严重 | 已有 RLS 与哈希化注册 IP；T8 数据清单与保留期；埋点白名单禁止上传 |
| 账本样本少且自报偏差 | P8 校准被噪声驱动 | T10 最小样本量门槛、去重、只展示不回写 |
| 姓名拼写意外持久化 | 隐私承诺被破坏 | 既有「不落库」约束以测试形式固定（T8） |
| staging 与生产迁移链不一致 | 上线失败或数据破坏 | 从空库重放迁移；PR #20 已中和历史 bootstrap 迁移 |

### 3.4 发布门禁风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 以「工程门禁通过」被误读为「预测有效」 | 与宪法「诚实」原则冲突 | 门禁文档与 UI 文案坚持「实现证据 ≠ 科学有效」 |
| Lovable 直接发布绕过 GitHub 审查 | 事实源分裂 | T9 策略：GitHub 唯一事实源，Publish 需门禁 |
| 为了 beta 时间压力放宽 `commercialReadiness` | fail-closed 被打穿 | 门禁参数变更须走 ADR 与测试；禁止手动 bypass（GATES 文档已规定） |
| 对 P6.1「已完成」的认知与仓库不一致 | 排期建立在不存在的基础上 | T3 首周核实并纠正 ROADMAP |

### 3.5 关键外部依赖

- 仓库 Owner：Actions 恢复、私有仓库计费。
- Supabase 管理员：凭据轮换、staging 项目。
- 幕僚长/用户：铁板底本授权、产品命名、Lovable unpublished changes 处置、备忘录内容。
- 文献来源：可引用的规则底本（子平真诠、增删卜易、太乙金镜式经等版本化引用）。

## 5. 附：本文档的「唯一目的对齐」段

本计划的每一项任务都服务于宪法（HPU-1）的唯一目的——「工程化、可追溯、可复现地呈现多种传统文化规则对同一输入的计算结果、分歧和证据边界」：T1/T2 恢复证据链与安全底线；T3 消除事实源分裂；T4 让轨迹节点可回溯到引擎与规则；T5/T6/T7 推进「先修核」而不假装完成；T8–T12 只在门禁框架内为 beta 铺路。任何与此段冲突的改动不应进入主分支。
