# 08 · 后端与数据

> 本次会话没有连接线上库，以下关于线上结构的陈述都来自 `supabase/migrations/` 与 `src/integrations/supabase/types.ts`。线上实际状态可能与迁移文件不一致（例如 Lovable 侧直接改过的部分），在第 5 阶段动手前需要导出线上 schema 核对（未核实）。
> 未经你明确同意，不对线上库做任何破坏性变更。下面所有「删除」「改名」都是计划，执行前逐项请你确认。

## 0. 结论先行

- **沿用现有 Supabase 项目**（10 文档 D11 建议），新表以增量迁移加入，旧表先保留只读，再分批退役。
- 敏感数据（出生信息、现实情境、他人信息）进入**独立的新表**，只有本人能读写，管理员也不能读；不进日志，不进分析埋点。
- 计算在客户端完成，服务端只存「输入 + 结果摘要」；完整结果可以由输入和算法版本重新计算出来，所以默认不长期存储完整的 `UniquePath`（用户可选择保存快照）。
- 第 0 阶段的安全前置：轮换凭据（只能由你在控制台操作）、合并 PR #20 的等价修复、清理明文密码迁移的影响。

## 2. 新表

所有新表都有 `user_id uuid not null references auth.users(id) on delete cascade`，并开启 RLS。

| 表 | 主要字段 | 说明 |
|---|---|---|
| `persons` | `id`、`user_id`、`person_key`（契约中的 PersonId）、`kind`（self / complete / derived）、`label`（默认关系称谓）、`birth`（jsonb，`BirthInput`）、`created_at`、`updated_at` | 一个用户的全部人物。`label` 不要求真实姓名 |
| `person_relations` | `user_id`、`from_person`、`to_person`、`role`、`year_from`、`year_to` | |
| `reality_contexts` | `id`、`user_id`、`version`、`as_of`、`payload`（jsonb，`RealityContext`）、`created_at` | 每次修改新增一行（版本化），用于比较新旧路径；用户可删除任意版本 |
| `analysis_runs` | `id`、`user_id`、`request_digest`、`algorithm_version`（jsonb）、`reality_version`、`summary`（jsonb：路径地址、各节点结果与概率、冲突摘要）、`created_at` | 不存完整回溯链；完整结果可由输入重算 |
| `path_snapshots` | `run_id`、`user_id`、`payload`（jsonb，完整 `UniquePath`） | 仅当用户主动「保存这一版」时写入 |
| `path_feedback` | `id`、`user_id`、`run_id`、`choice_id`、`kind`（happened / did_not_happen / different）、`year`、`note`、`created_at` | 用户对推演节点的事后反馈。这是未来校准的唯一数据来源 |

**RLS 策略**（全部新表相同）：

```sql
create policy own_rows_select on <table> for select using (auth.uid() = user_id);
create policy own_rows_insert on <table> for insert with check (auth.uid() = user_id);
create policy own_rows_update on <table> for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy own_rows_delete on <table> for delete using (auth.uid() = user_id);
-- 不为 admin / super_admin 建任何读取策略
```

`service_role` 只在删户函数中使用。

## 4. 存储、删除与日志

- **删除**：用户可以删除任一人物（连带其关系、出生信息）、任一现实情境版本、任一分析记录，或一键删除账户。删除账户时，`delete-account` 显式删除全部新表与冻结的旧表中该用户的行，再删除 `auth.users`（外键级联作为第二道保障）。删除是硬删除，不做软删除。
- **他人数据**：只归属于录入它的用户，只用于该用户自己的世界生成，不与任何其他用户的数据关联（即使两个用户录入了同一个人，系统也不做匹配），随该用户数据一并删除。界面默认显示关系称谓。
- **日志与埋点**：Edge Functions 不记录请求体；前端埋点（若有）只允许白名单事件名（如 `analysis_completed`），不带任何参数值；错误上报前剥离所有用户输入。这条写进 `CLAUDE.md`，并由一个静态检查脚本（禁止在 `console.*`、日志调用中引用 `BirthInput`、`RealityContext` 类型的值）辅助执行。
- **本地缓存**：IndexedDB 中的缓存只存当前用户的数据，退出登录时清除。

## 5. 从现有线上数据的迁移路径

1. **只读快照**：在第 5 阶段开始前，你在 Supabase 控制台导出线上 schema 和行数统计，我据此核对与迁移文件的差异（不导出数据内容）。
2. **增量迁移**：新表以新迁移文件加入，不修改旧表结构。旧前端在过渡期继续可用（如果你仍需要它在线）。
3. **旧账本不迁移到新契约**：旧 `prediction_runs` 的结构（10 维分数、旧引擎记录）与新契约不可比，硬转换只会制造看似连续的假数据。处理方式：
   - 冻结：撤销 insert / update 权限。
   - 告知：在新界面「数据与隐私」中显示「你有 N 条旧版分析记录（旧算法），可以导出或删除」。
   - 新用户首次使用新版时，从旧记录中**只读取出生信息**作为本人出生信息的预填建议，由用户确认后写入 `persons`（这一步需要你同意，D11）。
   - 一个版本周期后（时长由你定），删除旧表的 `birth_input` 列内容，或整表删除。
4. **回滚**：每个迁移都写对应的回滚迁移；在 staging 项目中先完整重放全部迁移（包括旧的 23 个）再上线。

## 6. 用户反馈

`path_feedback` 记录用户对推演节点的事后反馈（「发生了 / 没发生 / 以不同方式发生」）。它的用途和限制：

- 积累到足够样本前（例如每个选择类型、每个引擎至少数百条独立用户反馈，具体门槛在第 7 阶段的校准设计中确定），**只展示统计，不回写任何权重或参数**。
- 反馈数据在用于统计前做去重与反作弊（同一用户同一节点只计一次）。
- 用户删除账户时，反馈一并删除，统计结果在下次重算时随之变化。
