# 09 · 分阶段计划

> 不给日历时间。每个阶段结束时，重建分支上的仓库可运行、`pnpm check` 全绿、GitHub Actions 全绿（前提是 Actions 本身可用，见第 0 阶段）。

## 0. 对你提议的建设顺序的评估

你的顺序：时间历法地基 → 八字、紫微 → 立即打通一级世界、提取、二级世界、现实情境、坍缩 → 逐个补齐其余引擎。

**我同意这个顺序的主干**，理由也是你说的：六段式里最没有先例、最可能出问题的是第 3–6 段，越早端到端跑通，越早发现设计问题；两个引擎是体现「各自成世界」与跨引擎提取的最小数量。

**我做四处调整：**

1. **前面加一个第 0 阶段（工具链与安全）。** 现在从干净检出装不出依赖、CI 失败、安全门禁失败（00 文档 §1、§7）。不先修好它，后面每个阶段的「检查全绿」都无从谈起。
2. **契约在第 1 阶段一次定全（包括第 3–6 段的契约）。** 不能等做到第 4 阶段再定二级世界的契约，否则引擎层会按错误的交付形状实现。契约允许在后续阶段以「新增可选字段」演进。
3. **两个主干引擎做完排盘后，先做「单人」的端到端，再做「多人」。** 多人带来跨人物匹配、推导人物、增量缓存，复杂度高一级；先用单人验证六段的数学，能把问题定位得更准。
4. **第一个补充引擎选西方占星。** 八字和紫微同属中国历法族，它们的「一致」大部分是同源，不是独立印证（04 文档 §3.3）。西方占星来自不同的数据基础（行星位置），才能真正检验「跨引擎印证」和「干涉」是否按设计工作。而且它的天文计算部分可以用 JPL Horizons 做严格的数值验证。

还有一处**风险提示**：紫微设计文档建议的初始状态是 `needs_source_validation`。如果第 2 阶段结束时紫微的排盘黄金用例还没备齐，它在坍缩中的权重 ρ 只有八字的一半；同时八字第一版不给方向。两者叠加，第一版的唯一路径主要由现实情境和【自定】参数决定，引擎贡献的主要是「关口在哪里」。这是诚实的结果，但你需要预期到它。

## 1. 旧代码的去向

采用你的默认想法，并具体化：

1. 第 0 阶段开始时，给当前 `main` 打标签 `legacy-final-2026xxxx`（日期按实际），并推送到远程。
2. 新建重建主分支 `rebuild/main`（名字可改），所有阶段在其上进行，阶段内的工作用短分支向它提 PR。
3. 第 0 阶段把旧的 `src/`、`crates/`、`public/wasm/`、`scripts/`、`src/data/tieban-clauses.json` **移入 `legacy/`**（不删除），从构建、测试、lint、类型检查中排除。原因：旧代码会让新的检查无法变绿（旧 lint 错误、旧安全门禁失败），而它只是参考资料。
4. 之后每当新实现覆盖某块功能，就在同一个 PR 中删除 `legacy/` 下对应的目录。各阶段的退出标准中列出应当删除的内容。
5. 旧的 `docs/` 中被本套文档取代的文件在第 0 阶段移入 `docs/archive/`，并在文件头注明「已被 `docs/rebuild/` 取代」。
6. 重建分支达到第 5 阶段（可以上线）后，合并回 `main`。合并方式（直接合并 / 用新分支替换 `main`）届时由你决定。在此之前，`main` 和 Lovable 保持现状，你的线上服务不受影响。

## 2. 阶段

### 第 0 阶段 · 工具链、安全与基线

**范围**
- 打标签、建分支、移入 `legacy/`（§1）。
- 包管理器与唯一锁文件（D12）；pnpm workspace 骨架；所有 L0–L9 包建空壳，各有一个占位测试。
- CI 重写：`install → lint → typecheck → test → build → 静态安全扫描 → 确定性扫描`；先查明 Actions 3 秒失败的原因（可能是账号或计费层面，需要你在 GitHub 设置中查看）。
- 安全：你完成凭据轮换；把 PR #20 的方案改写为新分支上的迁移（只写文件，不碰线上）；`tieban_clauses` 读取策略收紧的迁移文件。
- `CLAUDE.md`、`docs/rebuild/宪法-v3.md` 定稿并放到最终位置；旧宪法与总规划移入 `docs/archive/`。

**产出**：可安装、可构建的空骨架；绿色 CI；安全迁移文件（未上线）。

**退出标准**
- 从干净检出执行 `pnpm install --frozen-lockfile && pnpm check` 成功。
- GitHub Actions 在 `rebuild/main` 上至少一次全绿，记录 run 链接。
- 静态安全扫描在新树上通过；仓库中不再有明文密码语句（`legacy/` 中的旧迁移也已移除或改写）。
- 你确认凭据已轮换。

**依赖**：D8、D9、D12 需要你先拍板（它们决定骨架怎么搭）。

### 第 1 阶段 · 地基：detmath、契约、时间历法

**范围**
- `detmath`：exp、log、sqrt、σ 的四则实现；规范十进制；`canonicalJson`；SHA-256；种子派生。
- `contracts`：02 文档的全部 schema，包括第 3–6 段的契约；导出 JSON Schema 供 Supabase 函数使用。
- `astro-time`：IANA 时区（含夏令时空隙拒绝、重叠须显式选择）、儒略日、真太阳时、节气、公历农历互转（含闰月）、干支、行星地心视黄经（封装 astronomy-engine 并量化）。
- `rule-registry`：格式、校验器，以及 astro-time 自身的规则（如「立春切年」）。
- `testkit`：黄金用例加载器、属性测试框架。
- 获取 06 文档 §7 中的第 1–5 项外部数据。

**退出标准**
- `detmath` 的每个函数与高精度参考值对比，误差 ≤ 1 ulp 量级（具体界写入测试）；在 Node 与 Chromium 中输出哈希相同。
- `golden/astro-time/` 中：儒略日 ≥ 200 例、节气 ≥ 2,400 个（1900–2100 年每年 24 个中抽样或全量）、农历对照覆盖 1901–2100 每年至少 1 个闰月或正月初一、时区 ≥ 50 例、行星 ≥ 500 个（时刻 × 天体），全部在容差内通过。
- 契约包 100% 有 schema 测试（合法与非法样例）。
- 静态扫描证明算法包中没有禁用 API。

### 第 2 阶段 · 两个主干引擎：八字、紫微

**范围**
- `engine-bazi`、`engine-ziwei`，按各自设计文档实现第一版规则清单；规则全部登记。
- 你在 D 系列口径决策（子时、真太阳时、起运折算、闰月、紫微流派与四化口径等，见两份引擎文档的「待决」项）上拍板。
- 获取 06 文档 §7 第 6、7、8 项数据。

**退出标准**
- 八字：排盘与大运时间轴的独立黄金用例四类各 ≥ 30 例，全部通过 → 状态至少 `partial`。
- 紫微：命身宫、五行局、十四主星、四化、大限的独立黄金用例 ≥ 100 例，全部通过 → 状态由 `needs_source_validation` 升为 `partial`；未达到则保持原状态并在下一阶段继续，**不阻塞第 3 阶段**。
- 两个引擎的输出全部通过 `EngineDelivery` schema 校验；`rulesUsed` 与登记表双向一致。
- 删除 `legacy/` 中旧的八字、紫微、日历实现。

### 第 3 阶段 · 单人六段打通

**范围**
- `world-model`（状态、目录、参数集 `params/2026.1`）、`worlds`、`choices`（单人）、`multiverse`、`reality`、`collapse`、`pipeline`（单人）。
- 最简界面：输入本人 → 现实情境问卷（最小字段集）→ 唯一路径页（深度 1、2）。
- Web Worker 集成。

**退出标准**
- 06 文档 §5 中所有与单人相关的数学性质测试通过，包括「动态规划 = 暴力枚举」（K ≤ 8）。
- 「单人版」例子（04、05 文档中只保留 A、去掉 B 与 F 的版本）作为端到端测试，数值与文档一致。
- 同一输入在 Node 与 Chromium 中的 `UniquePath` 字节相同。
- 单次分析（K = 12）在一台中端 Android 设备的浏览器中耗时被测量并记录（不设通过线，只记录，作为后续优化依据）。
- 删除 `legacy/` 中旧的世界树、坍缩、事件抽取、融合实现。

### 第 4 阶段 · 多人、推导人物、增量计算

**范围**
- 人物实体、`relationSlots` → 推导人物、跨人物联合事件、带人物参与者的阶段博弈、缓存与增量更新。
- 人物管理界面、第三方信息提示。

**退出标准**

- 「提取对人物顺序不敏感」等多人性质测试通过。
- 增删一个人物后，其他人物的引擎与一级世界缓存命中（测试断言引擎调用次数）。

### 第 5 阶段 · 后端与产品化（可上线的最小版本）

**范围**

**退出标准**

- RLS 测试：管理员账号读取他人 `persons`、`reality_contexts` 均被拒绝。

### 第 6 阶段起 · 逐个补齐引擎

**顺序建议**：西方占星 → 吠陀 → 数字命理 → （铁板，视 D7）→ 占问类问事模式（视 D5）。玛雅与卡巴拉按各自文档建议，第一版不进入世界生成，只做盘面展示，可以在任意阶段穿插。

**每加一个引擎的固定退出标准**
- 该引擎的排盘黄金用例按其文档的数量要求全部通过。
