# 太乙神数引擎设计（engineId `taiyi`）

## 1. 结论摘要

- 太乙神数的主体是**年计**：从一个极远的「上元甲子」起算到所求之年的「积年」，再按 72 局周期定局，推太乙、文昌、始击、主客算等，用来论国运、天时、兵事。它推的是「某一年的天下大势」，不是某一个人。
- 因此它既不是典型的本命类，也不是典型的问事类：年计的结果对同一年出生或经历同一年的所有人都相同。最贴切的位置是「时代」背景，而非用户本人。
- 「太乙人道命法」等论个人命运的内容，我只能确认这一说法在后世太乙文献与二手资料中被提及，**无法确认其所在典籍卷次与具体规则**，不纳入。
- 建议第一版**不进入**主流程。第二版两个候选用途：问事模式（时计太乙）、或作为「时代」层的年度背景信号；两者都要先解决积年起点问题。
- 旧代码的根本问题：积年起点没有可核实来源（`src/core/taiyi/constants.ts` 的 `DEFAULT_EPOCH_YEAR = -10153917`，注释自相矛盾），而局数、太乙宫、文昌、主客算全部由它派生；另有文昌「太乙宫顺行 4 步」等明确标为简化的自定规则。
- 建议初始状态：`experimental`。

## 2. 声明的流派和范围

**流派**：以《太乙金镜式经》为主、《太乙统宗宝鉴》为辅的年计太乙。`school` 写「太乙神数·年计·《太乙金镜式经》体系」。是否改用其他典籍的积年数，取决于用户能提供的书证。

**输入**：
- 所求年份（年计）或所求时刻（时计）+ IANA 时区。
- 不需要出生地、性别、姓名。若用于「时代」层，输入是用户一生覆盖的年份范围，与出生时刻无关。

**口径决策点（待决）**：
1. **积年起点与积年数**：太乙以「上元甲子」至所求年的积年为根。不同典籍、不同年代的书给出的积年数不同，旧代码注释中就并列了三种说法。必须由用户提供一部典籍中「某年积年为若干」的原文作为锚点；没有锚点之前，引擎不输出局数（见 §3 `taiyi.jinian.anchor`）。
2. **太乙年的边界**：太乙年以冬至、立春还是农历正月初一换年，我无法确定，需书证。旧核心代码直接用所在时区的公历年（`src/core/taiyi/calculateTaiyi.ts` 的 `gregorianYearFromUtc`），这几乎肯定不对。
3. **九宫编号**：我印象中太乙式盘的九宫数与奇门所用的洛书后天九宫编号不同（太乙有独立的宫数次第），而主客算是对宫数求和，编号不同结果就不同。这一点我不确定，需书证；旧代码直接沿用洛书编号。
4. **年计阴阳遁**：我印象中年计太乙只用阳遁，阴阳遁之分主要用于日计、时计。旧代码把 72 局拆成前 36 阳、后 36 阴，未注出处。需书证。
5. **大将、参将取数**：我印象中是「算数去十取零」（即取个位），参将为大将数三因之再取零；旧代码用的是对 9 取余。需书证。

### 2.1 本命类 vs 占问类：太乙如何参与「由出生信息推演一生」

**(a) 是否存在论个人命运的部分**

- 后世太乙文献及二手资料中提到「太乙人道命法」「太乙命法」，即以太乙之法推个人命运。我**不能确认**它出自哪一部典籍的哪一卷，也不掌握其规则细节，不清楚它是以出生年的年计局为基础还是另起一套。可靠性标 `unverified`。
- 我能确认的是：太乙的主体（年计、积年、局数、主客算）是论国运、天时与兵事的，与个人出生时刻无关。即便人道命法存在，它也必须先建立在可靠的积年起点之上，所以积年问题是任何用法的前置条件。

**(b) 两种参与方式（加一种本体系特有方式）的规则依据与风险**

| 方式 | 规则依据 | 风险 |
|---|---|---|
| 以出生时刻（或出生年）起局论一生 | 人道命法来源未核实；年计局对同年出生者完全相同，没有个人区分度 | 无可靠解读规则；容易把「国运年局」误当个人命运 |
| 问事模式：针对重大选择以某时刻起时计太乙 | 时计太乙在典籍中存在（卷章待查），但旧代码未实现，我对时计积时的具体算法没有把握 | 起点问题与年计相同且更敏感；规则缺口最大 |
| 「时代」背景：对用户一生覆盖的每一年给出年计局 | 年计是太乙最核心、记载最多的部分（卷章待查） | 依赖积年锚点与年界；解读（主客胜负论天下）映射到个人领域没有依据，只能作为时代描述，不能直接变成个人信号 |

结论：第一版不参与。第二版若参与，优先作为「时代」层的年度背景（只描述大势，`subjectRole` 不是任何个人），其次才是时计问事；论个人命运的人道命法不纳入，直到用户提供可引用的原文。

**(c) 各方式下分别交付什么**

- 时代背景模式：`chart` = `taiyi.yearly/1` 的数组（每年一个年计局）；`timeline` = 每个太乙年一个 `NativePeriod`（`unit: 'taiyi.year'`）；`signals` = 空。原因是主客胜负等结论论的是天下与兵事，不能映射到 `Domain` 中的个人领域。年局只作为世界层「时代」节点的描述属性提供，需要主设计者在契约之外为此留一个出口（见 §9）。
- 问事模式（时计）：第二版不实现，`omissions` 写 `{what:'时计太乙', reason:'not_implemented'}`。
- 出生起局：不交付任何信号；`omissions` 写 `{what:'人道命法', reason:'no_rule'}`。

## 4. 明确不做的部分

- **人道命法**：出处与规则都未能确认。
- **月计、日计、时计**：旧核心代码只是在 `scale !== 'year'` 时回退年计并警告（`src/core/taiyi/calculateTaiyi.ts`），并未实现；新设计在取得书证前不做。
- **阳九百六、三纪五元、大游小游、三门四户**：规则较多、来源卷章未取得，延后。
- **把主客胜负、格局吉凶映射为个人领域的信号**：没有依据。
- **任何分数**：旧代码 `confidence: 58`、`completenessScore: 60` 与 `FateVector` 都是捏造。
- 在积年锚点取得前，**不输出局数及其派生量**，以 `omissions` 说明。

## 5. 黄金用例需求

| 类别 | 需要什么 | 来源 | 格式要点 |
|---|---|---|---|
| 正常 | 至少 3 个不同年份的年计局：积年、局数、太乙宫、文昌、始击、主算、客算、大将、参将 | 典籍中直接给出某年积年与局式的原文；或至少两款太乙排盘软件交叉一致的结果（须记录软件所用积年数） | 期望值逐项注明出处页码 |
| 边界 | 局数周期首尾（第 72 局与第 1 局之间的换年）、太乙换宫之年、太乙年换年时点前后 | 同上 + 天文历表（若年界为冬至或立春） | 标注年界口径 |
| 非法 | 早于锚点或超出 `astro-time` 支持范围的年份；缺时区 | 无需外部数据 | 期望错误或 `omissions` |
| 歧义 | 换年时点落在时区差内（同一 UTC 时刻在不同时区属不同太乙年） | 时区数据库 | 期望 `ambiguous_input` |

**需要用户提供或外部获取的数据清单**：
1. 一段典籍原文：「某年积年若干」，附书名、版本、卷次、页码。这是整个引擎能否输出局数的前提。
2. 太乙年换年时点的书证。
3. 太乙九宫编号与主客算累计次序的书证（或可核对的式盘图）。
4. 文昌、始击起例的书证。
5. 若有：太乙排盘软件的名称、版本及其积年设置，以及若干年份的完整输出。
6. 若用户希望纳入人道命法：可引用的原文出处。

## 6. 向一级世界层交付的内容

**主流程（第一版）**：不交付。

**第二版「时代」背景模式（若采用）**：

- `timeline`：每个太乙年一个 `NativePeriod`，`periodId: 'taiyi.year.<公历起始年>'`，`unit: 'taiyi.year'`，`start`/`end` 为由 `astro-time` 按 `taiyi.year.boundary` 计算的换年时刻，`parentPeriodId: null`，`ruleId: 'taiyi.timeline.yearly'`。覆盖范围为用户一生涉及的年份。
- `key_node`：**无**。
- `tendency`：**无**。年计结论论天下大势，不能映射到个人 `Domain`；年局只作为时代描述，需要契约留出口（见 §9）。
- `relationSlots`：无。太乙年计体系内没有描述个人六亲的结构。
- 典型 `omissions`：`{what:'局数', reason:'no_rule', detail:'积年锚点未取得书证'}`、`{what:'文昌/始击', reason:'no_rule'}`、`{what:'人道命法', reason:'no_rule'}`、`{what:'月计日计时计', reason:'not_implemented'}`、`{what:'个人领域信号', reason:'out_of_scope'}`。

## 7. 它的一套世界如何展开

- 不产生分岔点，一个人一生的 key_node 数量为 0。依据：年计规则面向天下大势，不对个人「某时段某领域有变动」作出判断；人道命法未核实。
- 时代背景模式下，一个人一生约覆盖 80–100 个太乙年时段（数量即年份数），每个时段只携带年局描述，不影响世界数量。
- 时间映射：太乙年用绝对日期边界表示，世界层按日期把用户自身时段（如大运、流年）与太乙年对齐。

## 8. 从旧代码里可以借鉴什么

**可参考（仍需核对来源）**：
- `src/core/taiyi/constants.ts`：`SIXTEEN_GODS`（十六神位次，与我所知一致）、`JI_SHEN_MAP`（计神以寅为首逆行，注释引用了《太乙金镜式经》原句但未给卷章）、`BRANCH_PALACE`（地支配后天八卦宫）。
- `src/core/taiyi/calculateTaiyi.ts` 的结构：积年 → 局数 → 各要素 → 主客算，以及逐步写 `explanationTrace` 的做法；其中「积年可由 `epochYear` 覆盖」的思路可保留为「锚点可配置」。
- 局数取「(积年 − 1) mod 72 + 1」的形式与「积年除 72 取余」等价，可保留，但须先确定积年。

**已知问题与教训**：
1. **积年起点无出处且注释矛盾**：`src/core/taiyi/constants.ts` 中 `DEFAULT_EPOCH_YEAR = -10153917`，文件头注释写「公历前 10153917 年」，常量上方注释又写「公元前 10154193 年 / 一说 BC 10155908」。三个数互不一致，没有任何典籍卷次。所有派生量都不可信。
2. **太乙年 = 时区内公历年**：`gregorianYearFromUtc` 使用 `Intl.DateTimeFormat` 取公历年，忽略任何传统换年点。
3. **阴阳遁 36/36 拆分**：`src/core/taiyi/constants.ts` 的 `YANG_DUN_LIMIT = 36`，注释「积年 mod 72 < 36 阳遁 else 阴遁」，无出处，与我对年计用阳遁的印象不符（我的印象也未核实）。
4. **太乙宫行法与「每宫三年」不符**：`calculateTaiyi.ts` 中太乙宫按 `juWithinDun` 每局一步沿 `LOOP_ORDER` 移动，即每年换一宫；这与「每宫居三年」的通行说法不一致。
5. **文昌、始击为自定简化**：文昌 = 太乙宫顺行 4 步（代码注释「简化起例」）；始击 = 计神所临宫。
6. **主客算与大将**：`countSuan` 沿洛书八宫环序累加宫数，结果为 0 时返回起始宫号（`sum === 0 ? start : sum`），此回退无依据；大将参将用 `mod9`，与「去十取零」的说法不同（后者亦待核实）。
7. **元位 360 年「作示意」**：`yuanIndex` 的注释自称示意，无依据。
8. **测试无外部期望值**：`src/core/taiyi/__tests__/calculateTaiyi.test.ts` 只测确定性与取值范围。

**无依据的捏造（不得迁移）**：
- `src/core/taiyi/calculateTaiyi.ts`：`confidence: 58`、`completenessScore: 60`。
- `src/core/taiyi/toEngineOutput.ts`：主胜 65 / 客胜 35 / 平 50 作为十维 `FateVector` 的基准，`wisdom` 再 +5。
- `src/utils/taiyiAlgorithm.ts`：`calculateJiNian` 以「公元前 2697 年（黄帝元年）为上元」（`year + 2696`）；`calculateJuNumber` 用 `(jiNian * 3 + monthFactor + day * 5 + hourFactor * 7) % 72` 这种类哈希公式求局数；`calculateZhuKeSuan` 用 `(ju * 3 + 1) % 8`、`(ju * 7 + 5) % 8` 取主客宫。这些都是捏造，整个文件不应作为参考。
- `src/utils/eventSeedExtractors.ts` 的 `extractInstantEvents`：太乙判凶即归入 `health` 并生成「需注意健康与安全」种子，年龄窗口与概率为固定常数（详见 `qimen.md` §8）。读取的 `no['局式']`、`no['格局']` 键在核心适配器 `src/core/taiyi/toEngineOutput.ts` 的 `normalizedOutput`（键为 `juNumber`、`taiyiPalace` 等）中不存在。
- 起局时刻为点击时刻：`src/hooks/usePredictionFlow.ts` 第 98、159 行；`src/config/engineActivation.ts` 在 `natalAnalysis` 中激活太乙，理由写作「低权重趋势参考」。由于旧核心年计只取年份，同一年内多次运行结果相同，跨年运行则会变化。

## 9. 未决问题与风险

1. **积年锚点**是本引擎的生死问题：没有书证，引擎只能输出「不可算」。
2. 太乙年换年时点、九宫编号、年计是否只用阳遁、大将取数方法，都需书证；我在 §2 中写出的「印象」均未核实，不能作为实现依据。
3. 契约层面：年计结论属于「时代」而非任何 `RelationRole`。`EngineDelivery` 的 `Signal` 必须带 `subjectRole` 和个人 `Domain`，没有表达「时代背景」的位置。需要主设计者决定：是为世界的「时代」节点增加描述通道，还是太乙在第二版仍不参与。
4. 人道命法是否纳入，取决于用户能否提供可引用的原文。
5. 时计太乙用于问事，规则缺口最大，建议放到「时代」用途验证之后再评估。
