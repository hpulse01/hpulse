# 06 · 验证策略

## 0. 结论先行

- **验证分两类，分目录、分计数，永不混淆**：`golden/`（独立黄金用例，期望值来自代码之外）和 `snapshots/`（回归快照，由被测代码自己生成）。只有前者计入引擎晋级条件。现有仓库 556 个测试全绿、排盘却有错，就是两者混淆的后果（00 文档 §7.1）。
- **第 3 到 6 段没有外部标准答案**，用数学性质测试来验证：它们证明的是「代码忠实地实现了设计」，不证明「设计符合现实」。后者只能靠长期的用户反馈，文档和界面都必须如实区分这两件事。
- 引擎晋级 `complete` 是一个可执行的脚本检查，人工无法绕过。

## 1. 规则登记表

- 位置：`packages/rule-registry/rules/<engineId>.yaml`，字段见 02 文档 §4 `RuleRecord`。
- CI 校验：
  1. ruleId 格式合法、全局唯一，且一经发布不得改名（与上一发布版本比对）。
  2. `verified` 规则必须有 `work`、`edition`、`locator`，且被至少一个 `golden/` 用例引用。
  3. 引擎代码中出现的每个 ruleId 都在登记表中；登记表中 `produces` 非空的每条规则，在引擎代码中都有实现（双向一致）。
  4. `rulesUsed` 中的每个 ID 都存在。
- 登记表变更必须在 PR 描述中列出「新增 / 修改 / 降级」的规则，并附来源说明。

## 2. 黄金用例

### 2.1 目录与格式

```
golden/
├── SOURCES.md                         # 每批数据：来源、版本或网址、取得日期、取得人、许可
├── astro-time/
│   ├── julian-day.usno.jsonl          # USNO 儒略日
│   ├── solar-terms.hko.jsonl          # 香港天文台节气时刻
│   ├── lunar-calendar.hko.jsonl       # 香港天文台公历农历对照
│   ├── tz-history.iana.jsonl          # IANA 历史偏移（含夏令时空隙与重叠）
│   └── planets.jpl-horizons.jsonl     # JPL Horizons 地心视黄经
├── bazi/
│   ├── normal.jsonl  boundary.jsonl  invalid.jsonl  ambiguous.jsonl
└── <engineId>/ …
```

每行一个用例：

```json
{
  "caseId": "bazi.boundary.0007",
  "category": "boundary",
  "input": { "...": "BirthInput" },
  "expect": { "pillars.day": "庚寅", "omissions[].what": ["..."] },
  "tolerance": null,
  "ruleIds": ["bazi.pillar.day-boundary"],
  "source": { "kind": "external_chart", "ref": "SOURCES.md#batch-2026-11-hko", "checkedBy": ["<姓名缩写>", "<姓名缩写>"] }
}
```

- `expect` 只写外部来源给出的字段，用路径表达，不写整份输出。
- `source.kind` 只能是：`classic_example`（典籍成例，写明卷章）、`ephemeris`（天文历表）、`external_chart`（公认排盘软件或网站的结果，写明软件及版本）、`manual_derivation`（人工按规则表在外部排盘结果上推算，**必须两人独立推算并一致**）。
- 四类输入的含义：`normal` 普通输入；`boundary` 节气、子时、闰月、夏令时、高纬度等边界；`invalid` 应当被拒绝的输入（期望值是错误码）；`ambiguous` 存在流派或口径分歧的输入（期望值是 `ambiguous_input` 的遗漏说明，或在选定口径下的结果加上口径声明）。

### 2.2 独立性如何保证

1. **数据来源独立**：黄金数据只能由人从外部来源录入或用脚本从外部数据文件转换；转换脚本放在 `golden/tools/`，**禁止 import 任何 `packages/` 下的代码**（由 lint 规则强制）。
2. **流程独立**：新增黄金数据的 PR 与修改引擎代码的 PR 分开提交；黄金数据 PR 中不得出现引擎代码改动。
3. **计数独立**：`npm run report:golden` 分别输出「独立黄金用例数」和「回归快照数」，引擎状态只看前者。
4. **期望值不可由测试失败反向修改**：修改已有黄金用例的期望值，PR 必须写明外部依据（例如「HKO 表第 X 页更正」），否则 CI 中的「黄金数据变更审查」检查失败。

### 2.3 精度与容差

| 量 | 来源 | 容差 |
|---|---|---|
| 儒略日 | USNO | 精确到 1e-6 日 |
| 节气时刻 | HKO（分钟级发布） | ±1 分钟；落在容差内的出生时刻，引擎必须报 `ambiguous_input` |
| 行星地心视黄经 | JPL Horizons | ≤ 0.01°（月亮 ≤ 0.02°）；日期须覆盖 1900–2100，并包含离 J2000 至少 50 年的日期（以发现黄道历元错误） |
| 干支、宫位、星曜位置 | 外部排盘 | 精确匹配 |

## 3. 引擎状态晋级检查

`scripts/promotion-gate.ts` 对每个引擎输出一份「距离 complete 的剩余条件」清单，条件全部满足才允许把注册状态改为 `complete`（CI 比对注册状态与检查结果，不一致就失败）：

1. 声明范围内的所有规则都有 ruleId，且 `verification = verified`。
2. 声明范围内无缺失规则（`missingRules` 为空；超出范围的写入 `omissions: out_of_scope`，不算缺失）。
3. 独立黄金用例覆盖四类输入，每类至少 N 个（N 由引擎文档给出，例如八字每类 ≥ 30），且全部通过。
4. 引擎输出中没有死亡、寿命类字段（类型层面已不可能，此项做静态确认）。

`partial` 与 `needs_source_validation` 之间的区分也写成检查：排盘部分（chart 与 timeline）有独立黄金用例且全部通过 → 至少 `partial`；否则 `needs_source_validation`。

## 4. 确定性检查

| 检查 | 方法 |
|---|---|
| 静态扫描 | 算法包中禁止的 API（01 文档 §1）出现即失败 |
| 同输入同输出 | 对固定的 50 组输入，运行两次、在两个进程中运行，输出的 `canonicalJson` 字节完全相同 |
| 跨运行环境 | 同一组输入在 Node 与 Playwright Chromium 中的输出哈希相同 |
| 时区与语言无关 | 在 `TZ=Pacific/Kiritimati`、`TZ=America/St_Johns`、`LANG=tr_TR` 等环境下运行，输出不变 |
| 版本闸门 | 固定输入的输出哈希登记在 `snapshots/version-gate.json`；哈希变化而 `AlgorithmVersion` 未变化 → 失败 |
| 种子 | 抽样方案下，种子只由本人规范化出生输入派生；修改他人或现实情境不改变种子（测试） |

## 5. 第 3 到 6 段的数学性质测试

这些测试用 `@hpulse/testkit` 的随机生成器（**测试代码中**允许用带固定种子的伪随机数生成测试数据）构造大量小规模输入，逐条验证：

| 性质 | 断言 |
|---|---|
| 一级世界独立 | 对引擎 e 的交付物做任意修改，其他引擎的 `PrimaryWorld` 字节不变 |
| 分岔点计数 | `worldCount.log2 = branchPoints.length`；分岔点按 (ruleId, periodId, subjectRole) 唯一 |
| 提取对引擎顺序不敏感 | 打乱 `PrimaryWorld[]` 的顺序，`ExtractionResult` 字节不变 |
| 提取对人物顺序不敏感 | 打乱 `others` 的顺序，结果不变 |
| 合并的单调性 | 增加一个支持某选择的候选，该选择的权重不减 |
| 族折扣 | 同族两个引擎的合并权重 ≤ 异族同等权重的合并权重 |
| QRE 不动点 | 解出的 P_i 代入公式后残差 < 1e-12；λ = 0 时全为 0.5 |
| 穷举完备 | 每个阶段的策略组合数 = Π 各参与者策略数 × 2（机会）× 3（环境，若有）；组合概率之和 = 1（误差 < 1e-12） |
| 结果概率归一 | 每个节点、每个状态、每个引擎：Σ_o P_e(o) = 1；叠加后 Σ_o P_k(o) = 1 |
| 单引擎退化 | 只有一个引擎时，叠加后的概率与该引擎的博弈概率相同 |
| 无方向不干涉 | 所有 a = 0 时，叠加结果等于按 ρ 加权的经典混合 |
| 一致变尖、冲突变平 | 二元节点上，判断一致时叠加分布的熵 ≤ 经典混合的熵；冲突时 ≥（随机生成 10⁴ 例） |
| 地址与节点一一对应 | 对枚举出的全部节点：`addressOf(nodeAt(a)) = a`；不同地址的结果序列不同 |
| 历史概率归一 | 小规模下暴力枚举全部历史，概率之和 = 1 |
| 与现实矛盾的世界被排除 | 对任一事实，后验中与之矛盾的历史概率为 0 |
| 测量的正确性 | 后验 = m·P / Σ m·P，与暴力枚举逐位一致 |
| 动态规划 = 暴力 | K ≤ 8 时，前向—后向的边缘概率、Viterbi 路径、抽样路径与暴力枚举结果逐位一致 |
| 逐级坍缩嵌套一致 | 月精度路径投影到年精度，等于年精度路径 |
| 边界扩大时的稳定性（报告型） | K → K + 4 时输出 `StabilityReport`；这是报告不是断言，因为路径**允许**在边界扩大时改变，测试只断言报告被正确计算 |
| 安全边界 | 任何输出中不存在死亡、寿命类字段或文本（类型 + 文本扫描） |
| 现实情境归因 | 只改一项现实条目时，`PathDiff.causes` 恰好指向这一项 |

## 6. 例子作为端到端测试

04、05 文档 §5–6 的手算例子（A、B、F，4 个节点，R1 与 R2）在第 4 阶段实现为端到端测试：

- 输入固定为文档中的出生数据、参数与现实情境。
- 断言：各节点的博弈概率、叠加概率、后验概率与文档中的数值在 1e-4 内一致；R1、R2 的唯一路径与文档一致；`PathDiff` 的原因指向 `facts.residence[2017]`。
- **前提**：例子中八字排盘的节气时刻与起运日期取自 `lunar-typescript`，紫微排盘是我按口诀手算的；它们在 `golden/` 中有独立来源之前，这个端到端测试只算「设计一致性测试」，不算验证。
