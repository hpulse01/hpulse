## 1. 结论

1. **现有仓库不能作为重建的起点，只能作为参考资料。** 原因不只是重复和混乱，更严重的是：不少引擎的排盘本身就是错的，而现有测试把错误当成了期望值写死了。所以「`partial`」这个状态高估了现状。例如紫微命宫公式把「月顺、时逆」写成了「月加时」，导致绝大多数命盘的命宫错位；五行局表与纳音不符，而测试断言的正是错误值（详见 §3）。
2. **第 3 到 6 段在旧代码里基本是比喻，没有实质。** 旧坍缩的「振幅」平方后就是玻尔兹曼 softmax，相位只用于显示，从未参与计算，所以不存在干涉。旧世界树的分支是「按分数取前 K 个事件」，没有博弈，也没有穷举。坍缩种子只用了出生年份和性别（`src/utils/worldTreeGenerator.ts:678-682` 调用 `generateCollapseSeed(tree.birthYear, 1, 1, 0, 0, gender, 0, 0)`），所以同年同性别的所有人共用同一个种子。
3. **主流程现在本身就不确定。** `src/hooks/usePredictionFlow.ts:98` 和 `:159` 用 `new Date().toISOString()` 作为 `queryTimeUtc`。占问类引擎（六爻、梅花、奇门、六壬、太乙）在本命流程里按「点击时刻」起局，所以同一份出生信息每次运行的结果都不同。
4. **工程地基也是坏的。** `package-lock.json` 与 `package.json` 不同步，`npm ci` 直接失败；`bun.lock` 的依赖地址指向 Lovable 的私有镜像（`europe-west1-npm.pkg.dev/lovable-core-prod/...`），在本环境返回 403；去掉锁文件后 `npm install` 也报错（`Cannot read properties of null (reading 'edgesOut')`）。从干净检出无法可复现地装出依赖。
5. **安全问题仍未关闭。** PR #20（特权 RPC 绑定 `auth.uid()`）自 2026-08-18 起一直是草稿、未合并。当前主干的两个迁移文件里仍有对管理员账号明文重置密码的语句（位置见 §6，内容不复述）。仓库自带的 `npm run security:static` 正因为它们而失败。

## 4. 第 3 到 6 段旧实现：它们想表达什么，实质是什么

### 4.1 事件抽取（`src/utils/eventSeedExtractors.ts`，2,476 行）

- **想表达的**：把各引擎的输出翻译成带年龄窗口、领域、强度、因果说明的「人生事件种子」，再跨引擎合并。这个「引擎输出 → 事件」的环节在新设计里对应「一级世界的关键节点」和「重大选择」，方向是对的。
- **实质**：绝大多数事件的年龄和概率是写死的常数或取模结果，与盘面无关。例如八字「正官格 28 岁、45 岁」、婚姻一律 27 岁（`:363-447`）；紫微 `baseAge = 20 + palace.index * 3`（`:732`）；流月直接取 `report.palaces[monthOffset]`，没有按流月规则排宫（`:1036`）；铁板 `proj.career % 1000 < 400 ? 30 : ...`（`:93-94`）。这类映射一律不能沿用。
- **可以借鉴的**：①「`sourceFieldPath` + `sourceEvidence`」这种回溯字段的思路（新契约中的 `evidence`）；② 以大运、大限、流年四化等引擎自有时间结构为触发点的那一小部分（例如 `extractZiweiEvents` 的流年四化段 `:1000-1030`），作为「哪些盘面特征值得做关键节点」的素材清单，但每条都要重新找规则来源；③ `commercialSafeSeeds` 排除死亡类事件的意图，新设计改为在类型层面根本不存在这类事件。

### 4.2 坍缩数学（`src/utils/quantumMath.ts`，866 行）

- **想表达的**：每条世界线有一个复振幅，概率为振幅模方，引擎一致时更确定，不一致时更不确定；坍缩可复现；用扰动检验稳健性。这些意图都合理，新设计全部保留。
- **实质**：
  - `calculateAmplitude` 的模长为 `exp(-E / 2kT)`，模方即 `exp(-E/kT)`，归一化后就是玻尔兹曼 softmax。相位 `phase` 只写进结果，**从不参与求和**（文件自己的注释也承认「does not model physical interference」，`:167-179`）。所以「振幅」和「干涉」都只是名称。
  - 「势能」`E = -Σ w·log p` 中的 `p` 是各引擎自评的固定概率（例如 0.7），本身没有依据。
  - 「退火」「蒙特卡洛路径积分」「Rényi 熵」「纠缠惩罚」是在 softmax 外层再包了几层启发式，参数（温度 `1.5 - 0.15×共识数`、扰动幅度 0.05 等）都是自定的，没有记录理由。
  - 坍缩种子只取出生年和性别（§1 第 2 条）。
- **新设计的处理**：保留「振幅—干涉—测量」的数学形式，但要真的让相位参与计算，并且每个量都必须有定义（`05-现实情境与坍缩设计.md`）。旧文件不迁移任何代码。

### 4.3 世界树（`src/utils/worldTreeGenerator.ts`，789 行；`src/types/destinyTree.ts`）

- **想表达的**：命运是一棵随年龄展开的树，节点有状态（命运向量），事件之间有前置、互斥、增强关系，最后选出一条到「分析边界」的路径。这个骨架与新设计的二级世界一致。
- **实质**：状态是 10 维 0–100 分数；「自然漂移」表（健康每年 −0.5、50 岁后加速等，`:57-124`）、人生阶段加成（`:151-160`）、「因果积分」（`:182-205`）全部是自定常数，没有来源。终点 `ANALYSIS_HORIZON_AGE = 100` 实际上起到了寿命上限的作用。`EventCategory` 里仍有 `'death'`（`destinyTree.ts:17`）。
- **可借鉴的**：事件之间「前置 / 互斥 / 增强 / 转化」四种关系的类型设计（`UnifiedEventCandidate` 中的 `prerequisiteEventIds` 等字段），对应新设计中「前一个选择改变后续选择的可用策略」。

### 4.4 冲突解决（`src/utils/conflictResolver.ts`，580 行）与 HPU 世界树（`src/hpulse/worldtree/`）

- `conflictResolver` 在 10 维分数上做加权平均、多数表决和「贝叶斯形式的类比」，处理的对象是分数，而新设计里引擎不再输出分数，所以整体弃用。其中「冲突要显式报告、不能悄悄平均掉」的原则保留。
- `src/hpulse/worldtree/` 是「5 个阶段 × 10 维」的加权平均表，没有分支。其中「并列时按引擎固定序号决胜」「降级引擎不进分母」两条确定性处理值得借鉴。

在 `git archive HEAD` 导出的副本中，删除三份锁文件后执行 `npm install --legacy-peer-deps`（不加该参数会报 `edgesOut` 错误）：

| 步骤 | 结果 |
|---|---|
| `tsc -b` | 通过 |
| `eslint . --max-warnings=0` | **失败**：10 个错误、1 个警告，集中在 Lovable 新增的 `supabase/functions/mcp/index.ts`、`src/pages/OAuthConsent.tsx` 和 `src/integrations/supabase/previewAuthStorage.ts` |

### 7.2 一处天文层错误的复核

西方/吠陀子代理怀疑旧天文层用错了函数，我在副本中实际运行验证：`src/utils/astronomy/celestialPositions.ts:85` 调用 `astronomy-engine` 的 `EclipticLongitude`，它返回的是**日心**黄经。以本设计例子的出生时刻（1992-03-15 02:00 UTC）为例：火星日心 296.2°、地心 319.9°；金星日心 298.5°、地心 331.3°。旧版西方和吠陀引擎的行星位置因此错了二三十度。新核心 `src/core/western/planets.ts:36` 改用了 `Ecliptic(GeoVector(...))`，方向正确；但它输出的是 J2000 黄道还是当日黄道，我没有验证。
